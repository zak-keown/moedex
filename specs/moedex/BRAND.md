# Moedex rebrand

Part of [SPEC.md](SPEC.md). Shared contracts and limits apply.

## Rebrand: a separately installable Moedex distribution

**Outcome:** a user installs and runs `moedex`, sees **Moedex**, receives updates from `zak-keown/moedex`, and can keep stock Codex installed with independent local state. This is a product/distribution identity change; model providers and upstream protocol compatibility remain truthful and intact.

**Baseline inspected:** `codex-cli/package.json` exports `codex` as `@openai/codex`; `codex-cli/bin/codex.js` selects OpenAI platform packages and suggests OpenAI reinstall commands; `codex-rs/cli/Cargo.toml` exposes the `codex` executable; `codex-rs/utils/home-dir/src/lib.rs` resolves `CODEX_HOME` or `~/.codex`; `codex-rs/tui/src/updates.rs` checks OpenAI GitHub releases and the Codex Homebrew cask; `update_action.rs` invokes OpenAI npm packages. `.github/workflows/rust-release.yml` packages companion executables, publishes to the OpenAI npm scope, and includes upstream deployment integrations. Authentication includes a `Codex Auth` keyring service in `codex-rs/login/src/auth/storage.rs`. Model instruction templates contain the Codex self-name. These are concrete implementation anchors, not an exhaustive string-replacement inventory.

| ID | Requirement | Acceptance evidence |
|---|---|---|
| B1 | Public executable is `moedex` (`moedex.exe` on Windows); CLI help, completions, examples, executable errors, and launch commands consistently use it. Do not install a global `codex` alias by default. Retain compatible subcommands and flags. | Install alongside an existing Codex installation; both commands resolve independently. Exercise interactive launch, `--help`, `--version`, `exec`, `resume`, login help, and app-server entrypoints through packaged artifacts. Generated completions invoke Moedex. |
| B2 | TUI header, onboarding, status/about, notifications, terminal title, error guidance, README and distribution metadata say **Moedex** where naming this application. Identify it as an independent fork of OpenAI Codex with a source link. Existing upstream copyright, LICENSE and NOTICE attribution remain. | Snapshot coverage of branded UI and error paths; a reviewed inventory classifies remaining Codex/OpenAI strings as provider, upstream attribution, compatibility or defect. |
| B3 | Distribution home precedence is nonempty `MOEDEX_HOME` > nonempty `CODEX_HOME` compatibility override > `~/.moedex`. `CODEX_HOME` compatibility use must be visible in diagnostics because it can intentionally share stock state. Blank variables count as unset; an invalid explicit path fails instead of silently falling back. Keep existing path validation semantics. | Table-driven tests for absent, blank, valid, invalid and competing overrides; an integration launch with neither variable writes only beneath Moedex home. Launch with both uses `MOEDEX_HOME`. Diagnostics show effective home and its source without credentials. |
| B4 | Propagate the resolved home to same-host Moedex subprocesses, helpers and app-server components that currently rely on Codex home. Remote exec hosts resolve their own Moedex home using that host's configuration and filesystem semantics; never transmit the client's local path as a remote filesystem location. Default config, sessions, state databases, history, logs, caches and user-installed plugins/skills are isolated. Repository-local `.codex` configuration and skills remain supported unchanged in this release; do not introduce a second project precedence system during rebranding. | A same-host parent/child/helper fixture observes the same effective home. A macOS app-server/Windows exec-server fixture uses independently valid isolated host paths while preserving the intended session association. Parallel stock Codex and Moedex sessions use different stores under default configuration. Existing `.codex` project fixtures retain behavior. |
| B5 | First launch may detect an existing Codex home and offer import; it must never import implicitly. Provide a preview/dry-run and separately selectable settings, sessions and credentials. Default credential selection is off. Copy into the destination; never move, rewrite or delete the source. Conflicts default to skip; replacement requires explicit selection and a destination backup. Report incompatible items individually. | Preview leaves both homes unchanged. Cancel writes nothing. Tests cover source equals destination, symlinks resolving to the same home, conflicts, interrupted import, rerun/idempotency and mixed supported/unsupported items. |
| B6 | Import settings through typed parsing, preserving valid provider configuration while identifying home-bound paths and executable/hook configuration for review. Import sessions through supported rollout/database semantics, using a consistent snapshot or the existing store API rather than copying live SQLite files unsafely. Preserve resumability and provenance; do not silently mark imported projects trusted. | Import a fixture containing old settings, a session and a conflicting destination session; resume the imported session successfully and retain destination records. Existing source hashes remain unchanged. Sensitive values are absent from preview/logs. Imported trust is not elevated without selection. |
| B7 | Use a Moedex-owned credential namespace for both legacy keyring and current secrets storage. Explicit auth import reads the old backend through its adapter and writes the new backend through its adapter; do not blindly copy encrypted stores or export plaintext to staging files. Prefer fresh login if the backend cannot migrate safely. Preserve restrictive file permissions/ACLs. Log only category, counts and status. | Backend fixtures cover file, keyring and encrypted store import and failures. Moedex logout does not remove stock credentials. A scan of import preview, process arguments, logs and temporary artifacts finds no tokens. Provider refresh-token invalidation, if encountered, is surfaced as a sign-in requirement rather than hidden. |
| B8 | All downloads, install/reinstall guidance, update metadata and update actions resolve to fork-owned release channels. Initial supported channel is `zak-keown/moedex` GitHub releases; proposed npm namespace is `@zak-keown/moedex`, subject to ownership/availability verification before enabling it. An unconfigured channel disables automatic update actions and gives a fork release link. Never fall back to `@openai/codex` or the stock Homebrew cask. | Mock update responses and install-context tests prove every supported action selects the fork. No-channel and unavailable-channel cases leave the installation intact. Package wrapper recovery messages also target the fork. |
| B9 | Fork packaging includes matching companion binaries and resources needed by the selected features (including code-mode host, app-server, proxy, platform sandbox helpers and voice resources where shipped). Internal `codex-*` helper filenames may remain when private to the package; resolution must select the same installed release, never an unrelated binary found on PATH. Disable inherited upstream npm publishing, website deploy hooks, signing assumptions and external repository update jobs unless deliberately replaced with fork-owned equivalents. | Release-artifact smoke tests launch helpers with a conflicting stock installation on PATH. Validate package inventory, resource resolution, checksum manifest and OS-specific launch. CI dry-run cannot publish to upstream namespaces or call upstream deployment hooks. |
| B10 | Version identity includes Moedex distribution version, fork commit, upstream base commit/version and release channel. Human `--version` leads with Moedex; expose detailed provenance through a stable diagnostic/about surface. Preserve app-server protocol version/capability meanings; do not substitute the distribution version into compatibility fields. Use an independently ordered distribution version for updates. | Provenance fixture and packaged smoke test match the release manifest. A newer upstream-only release does not appear as a Moedex update. Existing app-server compatibility fixtures remain valid. |
| B11 | Retain `codex-*` Rust crate names, internal module names, app-server wire methods/fields, rollout format and established provider environment variables unless a separately specified change requires otherwise. Do not alter `CODEX_SANDBOX_NETWORK_DISABLED_ENV_VAR` or `CODEX_SANDBOX_ENV_VAR`. Rebranding is not permission to globally replace Codex strings. | Protocol/schema compatibility checks and rollout resume fixtures pass; source diff confirms sandbox constants and behavior are untouched. Any public compatibility exception is individually documented and tested. |
| B12 | Agent-facing application identity says it operates in Moedex, while model names, vendor attribution and authentication providers remain accurate. Do not imply that renaming the client changes ChatGPT/OAuth/API access, model ownership or provider entitlements. Do not rewrite historical conversation turns to rename Codex. Keep new context bounded and use the required contextual fragment abstraction for any newly injected fragment. | Fresh-turn integration fixture receives the intended identity once; resume preserves prior messages byte-for-byte. Login UI labels the real provider and uses supported existing auth flows. All new/changed user-visible strings have appropriate snapshots. |
| B13 | Publish install/support instructions with supported OS/architectures, home compatibility behavior, import commands, update channels and uninstall behavior. Place product guidance in the repository README or an agreed top-level Moedex file rather than general product docs under `docs/`. Uninstall removes the executable/package; deleting user data is a separate explicit action. | Instructions reproduce installation from the actual built artifact. Clean uninstall preserves both Moedex data and stock Codex installation/data. |

**Delivery sequence:** (1) identity inventory and distribution metadata seam; (2) CLI/TUI identity and home isolation; (3) optional import with credentials as a separate selection; (4) fork release packaging and update isolation; (5) cross-platform coexistence and packaged acceptance. Release availability depends on B8–B10; local development can proceed before any public package namespace is reserved. No publishing or migration is authorized by the act of writing this specification.

**Nonblocking choices to finalize before the relevant implementation:** logo, palette and ASCII mark; release numbering policy; npm namespace reservation and whether npm is in the first release; Homebrew tap/Windows package manager support; exact import command spelling. Proposed defaults are typography-only Moedex branding, independent `0.x` distribution versions carrying upstream provenance, GitHub releases first, and an explicit `moedex import codex` command with dry-run/selection options. These do not change the identity, isolation or compatibility requirements above.
