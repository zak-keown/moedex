# Moedex enhancement catalog

Research date: 2026-09-10. This extends [the initial fork survey](FORK-RESEARCH.md). It is a menu for product decisions, not an approved implementation roadmap.

The follow-up [Moedex specification](specs/moedex/SPEC.md) defines requirements and acceptance criteria for this catalog plus the actual product rebrand. Its [traceability table](specs/moedex/TRACEABILITY.md) maps all 51 workstreams.

## Reading the evidence

**Source** means implementation was inspected; **Tests** means test code was inspected, not executed; **Docs** means maintainer documentation only. **Proposal** is our adaptation or synthesis, not a claim that the referenced fork ships it. No candidate was installed or runtime-tested. Effort estimates describe a coherent implementation on this checkout: **S** localized change, **M** several modules and behavioral tests, **L** a subsystem or substantial integration. They are judgments, not delivery commitments.

The survey began with GitHub metadata for 100 most-starred and 100 newest forks, then followed specific implementations and related projects. It does not rank all 19K forks. Sources are pinned where inspected; links to a README alone do not establish implementation quality or novelty relative to upstream.

## Recommended starting portfolio

There are **50 candidates** below, grouped by behavior; some deliberately complement one another and should share an implementation. My recommendation is to prioritize reliability and inspectability before broader provider/platform reach.

| Priority | Candidate                                         | Smallest useful outcome                                                                           | Evidence that would justify keeping it                                                                                                    |
| -------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | O1 + O2: snapshot-bound review and bounded repair | Review a captured tree, report findings with that identity, and stop after a fixed repair budget. | Concurrent edits cannot make an old review appear current; no-progress repair terminates.                                                 |
| 2        | R1 + R2 + O3: reliable interrupted work           | Preserve the queue, show a recovery deadline, cancel stale resumes.                               | Simulated outage, user intervention and late timer events neither lose nor duplicate input.                                               |
| 3        | U3 + C10: delegation context and cost controls    | Enforce history limits, then attribute known usage to each agent.                                 | Spawn rejection happens before spend; unknown prices remain unknown rather than zero.                                                     |
| 4        | C12: stale-safe editing                           | Add an optional structured edit tool for one selected model.                                      | Benchmark fewer failed edits or retries without accepting stale targets.                                                                  |
| 5        | O10 + O11: boards and attention inbox             | Organize existing sessions and expose the ones needing action.                                    | Crash/reconnect reconciliation does not leave completed work permanently “running.”                                                       |
| 6        | C6 + C7: selective context with coverage          | Inspect a bounded indexed tree and report omissions.                                              | Answers cite correct material; excluded files are visible; token use falls on a fixed task set.                                           |
| 7        | C13: evidence-backed completion                   | Attach check results and artifacts to completion claims.                                          | Changed code invalidates earlier test evidence; unsupported claims remain visibly unverified. These are proposed acceptance outcomes, not results measured during this survey. Useful standalone smaller changes include U2 (temporary settings), U8 (draft copy), U11 (rich queue), and C7 (coverage reporting). Provider protocols (C11), cross-root rooms (O7–O9), commit provenance (P3), and Android (U10) deserve separate design work.

## What Moedex already has

The [local baseline audit](FORK-BASELINE.md) is pinned to `8e2afc09126c0cea4c282725fe68af43adad73d7`. It finds partial/full history spawning, model/effort selection, agent messages, lifecycle hooks, goal continuation and budgets, text queues, bounded retries, themes, usage statusline, compaction, V8 code mode, plugins/MCP, managed worktrees and memory foundations.

Consequently, “add multi-agent,” “add memory,” “add themes” and “add automatic continuation” are not useful roadmap entries. The proposals below extend their behavior. Notable limits observed locally: CLI queues reject images; estimated-cost status items are enterprise-scoped; goal idle continuation requires an available live thread; managed `--worktree` does not support code-review mode or relocating an existing resumed session. Those are scoped source observations, not a complete absence audit.
